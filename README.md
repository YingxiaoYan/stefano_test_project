# How to reproduce

Here explains how to reproduce the primary results of the support project using a workflow management system called [Snakemake](https://snakemake.readthedocs.io/).
Before running the workflow, some preparation is required. 
The commands provided in this document should be executed at the project root directory  (`<project>`) using a command-line interface such as Terminal (Mac/Linux) and Command Prompt (Windows) .

## Step 1: Directories

The directories for code, input, and output files need to be prepared according to the structure described below.
Please note that every script at this directory (`code/`) is designed to be run from the project root directory  (`<project>`).  
The scripts access directories using relative paths.

    <project>/               # Project root directory
     ├── code/               # All scripts. Directory including this README.md
     │
     ├── data/               # Data 
     │   ├── external/         # External sources, e.g. public databases
     │   ├── raw_internal/     # Raw input data, obtained internally.
     │   ├── processed/        # Processed data
     │   └── intermediate/     # Intermediate data
     ├── reports/            # Reports generated by scripts
     └── outputs/            # Main outputs
         ├── figures/
         └── tables/

If these directories are not yet prepared, please refer to the Appendix at the bottom of this document for a list of useful commands.

## Step 2: Copy code

Copy all the code to the directory `<project>/code/`. 
One easy way to accomplish this is to make a Git clone of the project repository using the following commands.

```sh
cd <project>                    # <project> should be replaced with the appropriate path
git clone <repository> code     # <repository> URL provided in the Project Information section
```

The subdirectories within the `code/` directory should be structured as shown below.

    ├── code/
    │   ├── envs/             # Software environment
    │   ├── external data/    # Steps involving data from external sources
    │   ├── projlib/          # Reusable code modules imported by other scripts
    │   ├── reports/          # Code that generates reports in `<project>/reports/`
    │   ├── rules/            # Snakemake rules
    │   └── scripts/          # Scripts (AWK, R, Python, etc.) 
    │   └── workflows/        # Individual workflows for separate tasks

## Step 3: Input files

Ensure that required input files are available under the `<project>/data/` directory.
The files are listed in the `<project>/code/MD5_data` file.
The integrity of the input data can be verified by comparing the MD5 checksums of the files with the values in the `MD5_data` file with the following command, assuming you are in the `<project>` directory.

```sh
md5sum --check code/MD5_data
```

## Step 4: Environment and workflow

To mitigate issues arising from software environment inconsistencies, the environment in which the scripts were developed has been saved and can be restored.

We use a container system called [Apptainer](https://apptainer.org/docs/user/latest/) to recreate the software environment.
This can be particularly useful when the computer being used for data analysis is blocked from internet access, likely due to security reasons.
Please ensure that the necessary management software is pre-installed.
For installation questions, please refer to the software's website.
Fortunately, Apptainer is often pre-installed on many HPC systems.

To begin, navigate to the `<project>/code/envs/` directory using the `cd` command.
Execute the following commands in the directory to build a container image.

```sh
[[ -r "environment.yml" && -r "Apptainerfile.def" ]] &&
  sudo apptainer build nbis_support.sif Apptainerfile.def ||
  echo "Both files are required.">>/dev/stderr
```

Once the container image (`nbis_support.sif`) is created, run the following command in the `<project>` directory.
It will reproduce all the primary results.
If a job scheduler or batch system (e.g. `sbatch`) is required, please modify the command accordingly to fit the specific requirements of the system.
For example, you may need to use a different command to submit the job to the scheduler or specify additional options or parameters in the command.
It is recommended to consult the documentation or user guide of the job scheduler or batch system to learn how to submit jobs properly.

```sh
# Make sure you are in the <project> directory before running the command below.
apptainer exec code/envs/nbis_support.sif snakemake -s code/Snakefile --cores all
```

If the analysis computer is blocked from the internet (e.g., Conda channels), an additional computer that can access the internet will be required.
The image of the software environment should be created on the second computer and transferred to the analysis computer.

# Individual files under `code/`

Here are some descriptions on individual files.

## In the root of `code`

* `constants.yml` : Contants used in analyses and visualization
* `LICENSE` : License for the code here
* `MD5_data` : MD5 check sum to verify input data integraty
* `Snakefile` : Snakemake's default input script storing the workflow

## In `reports/` and `scripts/` sub-directories

### File name

The name of each script file often reflects its function, following a specific naming convention.

`<what it does>-<sample set ID>-<details>[.s(tep )number].<extension>`

The `<sample set ID>` mentioned above indicates the set of samples analyzed by the script.
The list of sample sets is provided below.

* `s1` : samples from study 1
* `s2` : samples from study 2

### R and Rmd scripts

All R functions, except for those from the packages listed below, are primarily called with double colons (`::`) to specify the source package clearly. 

* in `R-core` (e.g. `base`, `stats`, `utils`, ...)
* in `tidyverse` (e.g. `dplyr`, `ggplot2`, `purrr`, ...)
* Packages for S3 methods (e.g. `predict`, `autoplot`, ...) unable to specify them using `::`
* Packages automatically attached by `::` (e.g. `BiocGenerics`, `S4Vectors`, `IRanges`)
* Packages often used in high local density (e.g. `kabelExtra`, `janitor`, `survival`)

All R code adhere to [the `tidyverse` **R style guide**](https://style.tidyverse.org/syntax.html) as closely as possible.
